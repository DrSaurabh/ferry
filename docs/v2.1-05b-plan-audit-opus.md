# Ferry 2.1 — A5 plan audit, reviewer 2 (Opus) — `v2.1-04-code-plan.md` rev 0

Focus: completeness/traceability (requirements rev 3 + design rev 1 incl. M1–M25), scope (V12), vision/UX fidelity, logging/acceptance, phase sizing. Buildability, phase dependencies, CI feasibility and platform facts are reviewer 1's area and are touched only where they change "done" or traceability.
Checked against: `v2.1-audit-brief.md`, `VISION.md`, requirements rev 3, design rev 1 (§13 M1–M25), `v2.1-03-design-audit.md`, `v2.1-03c-design-recheck.md` (D1–D4), `docs/agents/phase-brief.md`, `v2-06-build-log.md` (B27), and the current app code where a claim depended on it (cheap greps, noted per finding).

Overall: the plan is thorough and traceable — every requirement and every M row is mapped to a phase and named tests, CP101–CP130 are mostly faithful to the design, and the one deliberate deviation (CP112 `am kill` instead of `force-stop`) is justified. The findings below are gaps where a mapped item has no concrete file/test or where "done" can't actually be checked from this workspace.

## Findings

### PO1 — Medium — §2.1, Ph11 tests (`EventCatalogueTest`) — V11
**Problem.** The catalogue check runs one way only: every event name *used in code* must be in the catalogue. Nothing checks the reverse — that every catalogued event (and every intent's outcome) is actually emitted somewhere. Events that belong to no screen/tap (`notif`, `lock`, `poll.start/stop`, `work.run`, `conn`, `disc retry=`, `perm`, `dialog`, `clock`, `svc.stop reason=`, `play reason=`) can be silently forgotten by a phase agent, and the gap only shows after the user's trial days, when the G1 rule can't judge those intents. The §0.1 "logging is part of every feature" rule names only tap ids, `screen` and `err.shown`.
**Fix.** Add the reverse direction to `EventCatalogueTest`: each part-1 event must appear in `src/main` (grep for `"<name>"`), with an explicit `pending: PhNN` column/allow-list that Ph19's Done requires to be empty. Add "every event row your phase owns is emitted" to each phase's Done line.

### PO2 — Medium — §1.4 `ResumeScheduler`, Ph15 — V8, P14
**Problem.** The plan says when the periodic work `ferry-resume-send` is enqueued, stopped after 3 days and re-armed on app open, but never that it is **cancelled when the queue ends** (send done, cancelled, or resumed in the foreground by the user opening Ferry). Neither `ResumeDecision`'s outcomes (`Skip | StartService | PostTapToSend | StopChecks`) nor the staged test checks it. Result: after the first waiting send, a 15-min job runs forever — exactly what P14/V8 forbid, and a `work.run` line every 15 min in the logs.
**Fix.** `SendQueueStore.delete()` (done/cancel) calls `ResumeScheduler.cancel()`; `ResumeDecision` returns `StopChecks` for an empty/missing queue (defence in depth). `WaitForPcPartB` (and the NoExempt variant) asserts `getWorkInfosForUniqueWork` is CANCELLED/empty after the send; `ResumeDecisionTest` adds the "no queue" row.

### PO3 — Medium — §0.1 "inherited unchanged … `docs/agents/phase-brief.md`" — V12 (works first time for the agents)
**Problem.** `docs/agents/phase-brief.md` (verified) still points a fresh agent to the **2.0** documents as "the source of truth": `docs/v2-audit-brief.md`, `docs/v2-04-code-plan.md` §0/§6, `docs/v2-06-build-log.md`, decisions "B1, B2… continuing from the log", phase branch examples `ph0a`. A Ph11 agent that follows its brief literally reads the wrong plan and writes to the wrong build log; the 2.1 plan's own records (CP102: `v2.1-progress.md`, `v2.1-06-build-log.md`, B101+) and read order (§0.1) only win if the agent happens to read the plan first.
**Fix.** Before Ph11, update the brief (or add `docs/agents/phase-brief-2.1.md`) to name `v2.1-audit-brief.md`, `v2.1-04-code-plan.md` §0/§2/§3, design rev 1 §13, `v2.1-06-build-log.md`, `v2.1-progress.md`, B101+, branches `ph11`…`ph19`, and `python3 -m pytest -q tools`.

### PO4 — Medium — Ph11 Done, Ph19 Tests/Done, §4 — V11 (acceptance verifiability)
**Problem.** Three "done" conditions need files that live only in CI artifacts, which cannot be downloaded into this workspace (2.0 build log, B27: proxy 403 on the blob host; plan's own Ph19 risk says so for screenshots): Ph11 "a phone suite **artifact** shows a shipped `app-log.txt`"; Ph19 "report on the real phone-suite `app-log.txt` from Ph11 **committed as a fixture**"; Ph19 "Claude runs `review_logs.py` on the phone/TV suite logs of that run". As written an agent cannot verify any of them.
**Fix.** Use the route B27 already proved: the emulator jobs run `python3 tools/review_logs.py` on the PC folders' `logs/` after the suite (from Ph19; before that `verify_inbox.py device-log` prints the tail of the shipped log) and **print** the report/log into the job log; agents read it with `gh api …/jobs/<id>/logs`. The Ph19 fixture is copied from that job-log print. State this in Ph11/Ph19 Done.

### PO5 — Medium — §1.4 `HomeScreen` "overflow Something's wrong", Ph11 — L4, V11, V6
**Problem.** L4 (rev 3): phone "Something's wrong" is "in the top bar overflow … one tap logs a marker with the **current screen**". The plan puts the overflow item only on `HomeScreen` (Ph11). Verified in code: 2.0 phone screens have no shared top bar and no overflow menu at all — each screen draws its own `TextButton(Back)` (`PickerScreen:231`, `TransferScreen:84`, `FromPcScreen:167`, `PlayOnTvScreen:103`, `RemoteScreen:75`). With the button only on Home, the marker always says `screen=home`, and the user must leave the screen where the problem is (picker, transfer, preview) to report it. Ph13 separately rewires "every phone screen's top bar" for Back.
**Fix.** One `PhoneTopBar(title, showBack)` in `ui/common` (Back → dispatcher [H69], overflow ⋮ with "Something's wrong"), introduced in Ph11 and used by every phone screen; Ph13 then only changes its Back path. `BackEverywhereTest` (or a small `WrongMarkerTest`) asserts the overflow exists on each screen and logs `wrong screen=<that screen>`.

### PO6 — Medium — §1.3 `LogShipper`, Ph11 tests — L3, V11
**Problem.** The TV's logs are half of the evidence for the controller, zoom, PDF, B3 and caps, but TV shipping is neither planned concretely nor tested. `LogShipper`'s triggers are "after send, at background, every 10 min in foreground while connected"; the TV never sends and rarely backgrounds, and "connected to the PC" is undefined on the TV (it talks to the PC only for the outbox). The only TV log test (`TvLaunchAndFocusTest`) checks the line exists *on the TV*.
**Fix.** Define the TV trigger (ship when the outbox/info call to the PC succeeds, then every 10 min while the PC is reachable, and on `onStop`); add a TV host check `verify_inbox.py device-log --pc T --expect "device_name"` after the TV suite (PC-T exists already). Also state the phone trigger when only the controller was used (no send): ship on Home's PC check.

### PO7 — Medium — §1.2/§1.5 cast `document`, §5.1 T8 — T8, R7
**Problem.** T8 says documents are "also castable from the phone (R7/R1)" and the design adds cast `kind: document` "(one PDF/txt item from the phone)". The plan builds only the **TV** side (`CastModels` kind, `TvCastScreen` → `TvDocScreen`). On the phone there is no way to choose a PDF/txt: "From this phone" opens the media picker (verified: `PlayOnTvScreen` pushes `Screen.Picker(target)`, a MediaStore photo/video picker). No file, no test, and the T8 traceability row doesn't mention it — dropped silently.
**Fix.** Either (smallest, V12-friendly) record a decision that phone→TV documents move to the backlog and remove the `document` cast kind from 2.1; or add one Browse "From this phone" entry "A document…" using the system `ACTION_OPEN_DOCUMENT` (`application/pdf`, `text/plain`) → existing cast flow, plus a `ControllerTest` case casting `report.pdf`. Either way update §5.1 T8.

### PO8 — Medium — §1.1 `tools/review_logs.py`, Ph19, §5.3 — requirements §9, V11
**Problem.** §5.3 lists what "real logs" must decide (B2 `share.resolve` outcomes, B3 first-frame rotation facts, TextureView dropped frames, TV loudness/volume, Rewind/FF key codes, WorkManager timing, vivo kills/exit reasons). The review script only plans a daily summary and distress rules G1–G11; none of these facts is surfaced. So judging B2/B3 — explicitly "judged from the first real logs" (M2, M25-C11) — needs manual grepping, which is what the script is meant to replace.
**Fix.** Add a short "Facts to check" section to the report: per-step counts of `share.resolve` and their row texts; each `play event=first_frame` with `rotation`/view box/`dropped`; `key` codes seen on the TV that map to no action; `volume` events; `work.run` intervals; `app.start exit=` reasons; `caps`. One synthetic fixture per item in `test_review_logs.py`. No new rule machinery.

### PO9 — Medium — Ph13/Ph14/Ph17/Ph18 tests — U1, V6
**Problem.** U1 requires "an automated test walks every screen with both Backs". Ph13 says "Ph14 adds Preview, Ph18 Controller/Browse" to `BackEverywhereTest`, but neither Ph14's nor Ph18's test list mentions it (a phase agent works from its own list). The walk also omits the new setup steps (what Back does on step 2/3 is unspecified), Settings > About (Ph19), and the waiting banner. On the TV, U1's "remote Back = one level up" has no walk at all for the new layers (Menu overlay → zoom mode → viewer/doc → home); only fragments exist (`ZoomPanTest` "Back keeps zoom", `TvControlV2Test` `back`).
**Fix.** Put "extend `BackEverywhereTest` with <screens>" in the Tests list of Ph14, Ph18, Ph19; define setup Back (previous step; on step 1 leave the app, setup resumes next start) in Ph13. Add one TV test `TvBackLevelsTest` in Ph17: Menu open → Back closes menu; zoom mode → Back leaves zoom mode; doc/viewer → Back to home.

### PO10 — Medium — §3 Ph11 (and Ph18) — phase sizing
**Problem.** Ph11 is the widest phase and everything depends on it: the complete catalogue for all of 2.1, `:core` logging, PC endpoint/store/migration, `pc.yml` changes, app wiring (AppGraph switch from RingLog, ActivityLifecycle fg/bg, exit reasons, LogShipper, DeviceNames, Settings switch + name field, WrongDialog, Navigator logging), tap ids on all 71 existing clickables (counted with grep), version rule, and it must pass **all** emulator suites (`[emu]`, log path change). An interruption mid-phase leaves `main` blocked for every later phase. Ph18 (~1 600 lines: controller UI + Browse + CastService/poller/idle/locks + notification fallback + 5 instrumented classes) has the same shape.
**Fix.** Split Ph11 into **Ph11a** (catalogue, `:core` EventLog/LogStateStore/LogReader/`postLogs`, PC endpoint + store + migration + paths, version rule; JVM/pytest + one `[emu]` run for the path change) and **Ph11b** (app wiring, tap ids, Settings, shipping + `LogShippingTest`). Optionally split Ph18 into service side (TvPoller, CastService idle/locks, cast notification, TV button) and controller UI (screen, pad, Browse).

### PO11 — Low — §1.4 `UploadItemFactory`, Ph14 — L5
**Problem.** L5's phone part ("for HEIC/videos the phone sends what it read: date taken, GPS present, original vs location-stripped") is planned only in the `fromShared()` row ("fills `ItemMeta` … GPS via `ExifInterface`"). The main sending path is the picker (`UploadItemFactory.fromPick`, verified), and videos have no EXIF (`ExifInterface` doesn't read MP4 location). An agent can satisfy the plan with share-only metadata, leaving most PC lines as `taken ?`.
**Fix.** Say in Ph14: `ItemMeta` is filled for picker **and** shared items; taken = MediaStore `DATE_TAKEN` (EXIF `DateTimeOriginal` for shared streams); GPS = EXIF for images, `MediaMetadataRetriever.METADATA_KEY_LOCATION` for videos, else `unknown`. `ItemMetaTest` covers a picked video.

### PO12 — Low — §1.4 `PreviewScreen`, Ph14 vs Ph16/Ph18 — P12, U7
**Problem.** P12 requires the preview to show "the U7 warning when a TV is known". `PreviewScreen` is built in Ph14, but caps (`TvStateV2.caps`, `CapsCheck`) arrive in Ph16 and are wired on the phone only in `PlayOnTvScreen` (Ph18). No phase owns "preview shows the warning", and `PreviewTest` (Ph14) can't test it.
**Fix.** Ph18 Files: "`PreviewScreen` top line adds the `CapsCheck` warning when the last TV's caps are known"; a unit case in `ControllerStateMapTest`/`CapsCheckTest` for the preview text.

### PO13 — Low — Ph18 `ControllerTest` description vs §5 — R10, M21
**Problem.** §5.1 maps R10 to "`ControllerTest` (resume reconnect; TV gone → message)" and §5.2 maps M21 (Browse opens at once when the TV is idle) to `ControllerTest`, but Ph18's own description of `ControllerTest` lists only key/seek_to/text/zoom/volume/open. The phase agent works from Ph18's list.
**Fix.** Add to Ph18 `ControllerTest`: idle TV → Browse sheet open on entry; stop the loopback receiver → "TV not found — is Ferry open on the TV?" + Try again; restart it + `ON_RESUME` → reconnected within ~2 s.

### PO14 — Low — §2.4 answers `409 ignored:<why>`, Ph18 — V5, V7 (uncertain)
**Problem.** The TV now tells the phone *why* an action did nothing (`no_player`, `not_zoomable`, `no_text_field`, `volume_fixed`, `not_foreground`), but the plan gives the phone no wording or behaviour for these, nor for an `api<2` TV beyond the message (does the pad stay visible though no `key` works? V7). Agents will either show raw codes, a generic error, or nothing — the touch pad silently doing nothing is the worst case. Whether `not_foreground` can occur (server alive while Ferry's TV activity is in the background) is **uncertain**.
**Fix.** In §2.4 add one line: `not_foreground` → status line "Ferry isn't on the TV screen — open Ferry on the TV"; other `ignored` results → no message (log only); `api<2` → only the old-TV message + Browse/Play-on-TV, pad hidden. Cover in `ControllerStateMapTest`. (Also: test texts should use the CI PC's name, not "Saurabhs-PC", V13.)

### PO15 — Low — §2.1 part 1 columns — clarity for Ph11
**Problem.** Part 1 is defined as `| event | layouts | fields | level |`, but the next paragraph makes `EventCatalogueTest` depend on "column `notes` in part 1" listing required tap ids and a "`required`" marker that no column holds. The Ph11 agent must invent the schema that both the Kotlin test and `review_logs.py` parse.
**Fix.** Define part 1 as `| event | layouts | fields | level | notes |` and say exactly what `notes` may contain (e.g. `tap ids: send, tv, …` = these ids need an outcome row in part 2), or drop the tap-id/outcome coupling and let PO1's reverse check carry it.

### PO16 — Low — small design points not carried into the plan — U9, U2, T8, §12, §2/§3
**Problem.** A few design/requirement details have no file or test line, so a phase agent may skip them: (a) U9 "with … a picture" / design §5.5 "an illustration (drawn vector)" on the stop card — M23 keeps it, the plan doesn't mention it; (b) U2 "the feature that needs it shows a one-line banner with Fix" — only refused media is planned/tested; notifications (send screen) and battery (waiting send) banners are unassigned; (c) T8 "Other document types: not supported (message says so)" — no text or owner; (d) design §12 "fallback switch in code if TextureView performance is a problem" — the plan only has the rotation constant; (e) §2 text debounce 300 ms, Browse photos `open` with all outbox photos + `start` index; §3 zoom-mode badge text.
**Fix.** One line each in the owning phase's Files (Ph13 a/b, Ph17 c/d/e-badge, Ph18 e). For (d) a `USE_TEXTURE_VIEW` constant is enough (video zoom simply hidden when false).

### PO17 — Low — CP115 cast notification fallback — V12
**Problem.** If `androidx.media:media` is not already on the classpath, the plan builds a `DecoratedCustomViewStyle` with a custom 5-button `RemoteViews` layout to avoid a dependency. A hand-made notification layout is more code and more device-specific rendering risk than adding `androidx.media:media` — an AndroidX library, which the constraints allow with a decisions-log row (verified: it is not in `libs.versions.toml` today; whether `media3-ui` brings it transitively is **uncertain**).
**Fix.** Fallback = add `androidx.media:media` (decisions-log row) and use `MediaStyle`; drop `notif_cast.xml`.

### PO18 — Low — §2.1 part 3 G6 — L6, V11
**Problem.** G6 flags `app.bg` while a `send.start` is open. Leaving Ferry during a send is the designed, normal path ("Back goes Home, the send continues", notification). Every real send where the user switches apps becomes a distress signal, burying the real ones (kills).
**Fix.** G6 fires on `app.start exit≠user` (killed) mid-task and on `app.bg` mid-`play`/controller only; backgrounding during a send is reported in the daily summary, not as a signal. (L6 says "backgrounded or killed mid-task"; this reads it for the tasks where backgrounding is abnormal — record as an [H] if adopted.)

## Checked and found sound (no finding)
- **Traceability:** every requirement (B1–B4, U1–U9, P11–P14, R1–R11, T7–T11, L1–L7, A1–A3) and every M1–M25 row (incl. C1–C15, D2/D3) maps to a phase and named tests. Apart from PO5, PO7, PO11, PO12 and PO16, each has concrete files. P12 for Play on TV is free: `PlayOnTvScreen` reuses `PickerScreen` (verified), so the Ph14 ▶/long-press preview covers both.
- **CP101–CP130 vs design/VISION:** no contradictions. CP112 (`am kill` instead of M15's `force-stop`) is a justified correction that matches M5 ("force-stop not promised"). CP118's `409 ignored` reuses 2.0's 409 "refused" (verified in `CastReceiverServer`), so 2.0 phones see nothing new.
- **Scope (V12):** apart from PO17, nothing is heavier than the design asks. The three-table catalogue, `.last-seq` dedupe, key-injection reference test and in-CI guide build all come from M6/M8/M18/CP123.
- **Wording:** quoted texts match M4/M5/M23/M24/M25 (C10, D2). Version comes from `VERSION_NAME` (C8).
- **Logging design:** ids on control requests, clock offsets from `/info`/`/logs`/state `time_ms`, `src=` on keys, monotonic `seq` across restarts, and the PC always at Detailed give enough to merge and correlate. PO1, PO4, PO6 and PO8 close the gaps between "designed" and "can be judged".
