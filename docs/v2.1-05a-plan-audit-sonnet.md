## High

### PS1 — The staged WaitForPc job cannot test what it claims: `am instrument` and `run_class` force-stop the app
- **Section**: §3 Ph15 (staged job, CP112, CP113), §4.4; VISION V1/V2 (this is the proof for "a send waits and survives").
- **Problem**: Every phase of the job is an instrumentation class run through `run_class`. (a) `run_class` begins with `adb shell am force-stop "$PKG"` (run_instrumented.sh line 250), and the suite-line "before" steps (`kill_app; start_pc_again A; run_resume_job`) run after it. A force-stop cancels the package's JobScheduler jobs and removes its notifications, so `run_resume_job` finds no WorkManager job (the dumpsys grep in CP113 comes back empty) and the process-death step is vacuous (CP112 says "a force-stopped package's jobs do not run", but the harness force-stops anyway). (b) Independently of the script, by default `am instrument` restarts (force-stops) the target package when instrumentation starts and when it finishes (`--no-restart` exists on recent Android; **uncertain** which API 34 behaviour applies). So the periodic job and the "Waiting for PC" notification are probably already gone when PartA ends. (c) PartB then starts a fresh instrumentation: if anything in app start (re-arm "on app open", Home banner) resumes the send, PartB passes without `ResumeSendWorker` ever running, because it only asserts "queue file disappears + 3 files on PC-A".
- **Fix**: Drive stage B from the host only. PartA's `after` field does `kill_app; start_pc_again A; run_resume_job; wait_sent A` (poll the inbox with `verify_inbox.py` for ≤ 60 s). Make the debug explicit-component broadcast `app.ferry.debug.RUN_RESUME_WORK` (cold-starts the process, enqueues `OneTimeWorkRequest<ResumeSendWorker>`) the primary trigger, not the CP113 fallback; keep the `cmd jobscheduler run -f` attempt as best-effort logging (on API 34, WorkManager 2.10 may use a JobScheduler namespace, so the plain `run` may not find the job; **uncertain**). Require the host check to also see the worker's own log line (`work.run found=yes`, then `send.resume`, catalogue O9) in the shipped `app-log.txt`, so a foreground-resume cannot satisfy it. If a PartB class is kept, it only asserts final app state after everything finished.

## Medium

### PS2 — The "without exemption" variant asserts a notification in a class that starts after the worker ran
- **Section**: Ph15 step 3 (`WaitForPcNoExemptA/B`, UiAutomator taps "Saurabhs-PC is back — tap to send"), §4.4.
- **Problem**: Force-stop (explicit or from instrumentation start) clears the app's notifications. The notification the worker posted before PartB starts will not be there for UiAutomator in PartB. Same root cause as PS1. Also, `idle_whitelist` state persists across classes; the plan runs "on" then "off", so the end state is right only if the "off" variant is last and its `after` always runs (it does, `after` is unconditional).
- **Fix**: After the forced run, assert the notification from the host: `adb shell dumpsys notification --noredact | grep -c "is back"` (retry ≤ 30 s). Cover the tap with a JVM/instrumented test of the PendingIntent's target (`MainActivity` extra → starts the service) or a host `am start` with the same extras. Do not add a UiAutomator class after the trigger.

### PS3 — Removing `ringLog` breaks five existing androidTest files (and the `app-build` job compiles them)
- **Section**: §1.2 `RingLog`, §1.3 `AppGraph`, CP108, Ph11.
- **Problem**: `AppGraph.ringLog.snapshot()` is called in `RetryAfterRestartTest`, `ShareLocationAllowTest`, `LaunchHelpers`, `TvPcNotFoundTest`, `SendHelpers` (`logged()`, `finishedRuns()` counts the text " engine finished:"). Plan says EventLog "replaces `ringLog`" and the shim keeps `AppGraph.log(tag,msg)`, but not the accessor. `assembleDebugAndroidTest` fails to compile → every emulator suite and `main` red. Also the shim turns the lines into `diag tag=… msg="…"`; the substring checks still work only if the message is not altered by quoting/escaping or truncation (2 KB).
- **Fix**: Name in Ph11: keep `AppGraph.ringLog` as a property returning an object with `snapshot()` (the EventLog in-memory tail), record it, and list these five files as "unchanged, must compile". Add to `EventLogTest`: a message with quotes and a colon still contains the original text for `contains()` use, or document that tests match on the unescaped prefix.

### PS4 — Persisted `seq` (written every 2 s) can repeat numbers after a crash; the PC then drops the lines that matter most
- **Section**: CP109, §2.2, §2.3 ("lines with `seq ≤` stored last are dropped").
- **Problem**: `ferry-log-state.json` is written at most every 2 s. After process death (the case G6 exists for), `seq` restarts at the stale persisted value, up to 2 s of numbers already used and possibly already shipped. The PC drops every new line with `seq ≤ last` as a repeat, so the first lines after a crash are lost silently, and "shippedSeq advances to the reply's `last_seq` only" keeps the phone cursor behind. `LogReader.linesAfter` would also re-send nothing useful.
- **Fix**: At start, derive `seq` from the last line of the current log file (authoritative), `max(file tail, state file) + 1`; or add a fixed jump (`+1000`) on every start and let `gap` mark it. Add an `EventLogTest` case: write lines, simulate a crash before the state save, restart, assert strictly increasing `seq`.

### PS5 — `ExifProbe` reads only `DateTimeOriginal`; the committed fixtures carry only `DateTime`
- **Section**: §1.1 `ExifProbe`, Ph12 tests, Ph14 (`verify_inbox.py readable-line --expect "taken 2025"`), `make_fixtures.py`.
- **Problem**: `android/ci/make_fixtures.py` writes `ExifTags.Base.DateTime` (IFD0 0x0132) into `gps.jpg`; I confirmed `2025:01:01 12:00:00` is in the file but no Exif sub-IFD 0x9003 is built. The plan's probe goes IFD0 → 0x8769 → 0x9003 only, so `taken` is `None` for every CI fixture, the PC line says `taken ?`, and the Ph14 host check fails. The phone side (`ExifInterface.TAG_DATETIME_ORIGINAL`) has the same blind spot.
- **Fix**: Probe falls back to IFD0 `DateTime` (0x0132) when 0x9003 is absent (also real-world useful), and add a `DateTimeOriginal` case to the generated fixtures in `test_exif_probe.py`. Do not regenerate `gps.jpg` unnecessarily (hash is computed at run time, so either works).

### PS6 — `ShareOriginalTest` as described cannot fail on the old code, and needs a `sharehelper` change that is not in the file list
- **Section**: Ph14 tests (`ShareOriginalTest`), §1.4 `UploadItemFactory`.
- **Problem**: `sharehelper` (`ShareActivity.FILES`) shares three generated pattern files, no GPS photo, and is not listed among the changed files. A FileProvider URI is not a MediaStore or documents URI, so `MediaStore.getMediaUri` returns nothing; only the M4 step 3 (name + size + date, exactly one candidate) can find a MediaStore original, and that needs a shell-pushed DCIM copy with the same name, size and mtime as the helper's file. The asserted result ("PC copy byte-identical with GPS") is also true for the plain copy-from-FileProvider path, so it does not prove resolution. The meaningful assertions are "no location dialog" and `share.resolve` naming the step.
- **Fix**: List `android/sharehelper/**` in Ph14 (a GPS photo mode: write `gps.jpg` bytes, `setLastModified` to match a host-pushed DCIM copy). Assert on the `share.resolve` event (`step=3 candidates=1`) and on the absence of `location_without`, plus a second method with two candidates → "as shared" and the note.

### PS7 — Seeding more files into PC-T breaks the existing TV and API 25 tests; plan names only some adaptations
- **Section**: §4.7, Ph17 tests, §1.6 `run_instrumented.sh`.
- **Problem**: `start_pc_tv` serves both the TV suite and the API 25 suite. `TvLaunchAndFocusTest` asserts the exact outbox order `big.mp4, small.mp4, photo1.jpg, broken.jpg, Test.apk, notes.txt, old.avi` and moves by row (`videos`, `photos`, `apps`, `other`); `TvHelpers.focusCard` indexes cards. Adding `portrait.mp4` (a Videos card), PDFs and a text file, plus a Documents row (and `.txt` becoming kind `text` after Ph12), changes row counts and indices for `TvLaunchAndFocusTest`, `TvResumeTest`, `TvLongPauseTest`, `TvSlideshowTest`, `TvScreenshotTour`, and the API 25 run of `TvLaunchAndFocusTest`. Only `TvPcNotFoundTest`, `TvSlideshowTest`, the tour are called out.
- **Fix**: Keep PC-T's seed unchanged and serve the new fixtures from a separate host PC (e.g. PC-D on 18770, started only in the TV suite and used with a `pcD` arg by the new classes), or append them so existing indices do not move and list every adapted class in the Ph17 build-log section. Tell the Ph12 agent that `notes.txt` becoming `text` is invisible to the 2.0 home (it falls under `other`), so no change is needed before Ph17.

### PS8 — `SetupFlowTest` ("fresh install") and the adapted `PhonePermissionTour` change state that later suite classes depend on
- **Section**: Ph13 tests, `suites/phone.txt` order.
- **Problem**: A fresh first-run setup needs `pm clear app.ferry` (resets Prefs and revokes grants, including `POST_NOTIFICATIONS`, which the script grants once at start). The suite chain is state-dependent: `PartialAccessBannerTest` expects a fresh install with only "Select photos", the next lines `grant READ_MEDIA_IMAGES…`, `GpsOriginalTest | grant ACCESS_MEDIA_LOCATION` assume earlier grants persist. Running setup mid-suite either needs `pm clear` (breaking that chain) or cannot show all 4 steps (the steps already granted are skipped by design, `SetupPlanTest`). Tapping "Allow" on the battery page also leaves the app on the deviceidle allowlist for later classes.
- **Fix**: Put `SetupFlowTest` last in `phone.txt` (before the tours) with an explicit host step `pm clear`, and `idle_whitelist off` in its `after`; decide whether the adapted `PhonePermissionTour` keeps its early slot (it uses the real first send) and say that setup is pre-completed there through `LaunchHelpers.cleanPrefs(welcomeDone=true)`.

### PS9 — Ph19's "Claude runs `review_logs.py` on that run's logs" has no way to get the logs out of CI
- **Section**: Ph19 Done and tests ("report on the real phone-suite `app-log.txt` from Ph11 committed as a fixture"), CP110, §4.3, `run_instrumented.sh` cleanup.
- **Problem**: Artifacts cannot be downloaded into the agent workspace (B27/B38); the suite works around it only for PNGs (base64 in the job log). Shipped device logs under `data/logs/<device>/app-log.txt` and PC logs are not printed anywhere; the `cleanup` trap copies only `data/ferry-*.txt|log`, which after the CP110 move no longer matches `data/logs/…` at all, so even the artifact loses the PC logs. Without a path, the acceptance step and the committed real-log fixture cannot be done.
- **Fix**: In Ph11, extend `cleanup` to copy `data/logs/**`, and have `run_instrumented.sh` print each suite's PC log and shipped `app-log.txt` between `FERRY_LOG_BEGIN/END` markers (gzip + base64, like the PNGs) plus a small `logs_from_log.py`, or simply run `python tools/review_logs.py` inside the suite step and print its report to the job log/summary. State which one in Ph19.

### PS10 — `docs/agents/phase-brief.md` still points agents at the 2.0 plan and records
- **Section**: §0.1 ("Inherited unchanged from the 2.0 plan §0.1 and `docs/agents/phase-brief.md`"), Read order.
- **Problem**: The brief tells the agent to read `docs/v2-audit-brief.md`, `docs/v2-04-code-plan.md` §6 and `docs/v2-06-build-log.md`, to append to `v2-06-build-log.md`, and to end commits with its own co-author trailer (Opus 5.5, an older session URL). The 2.1 plan puts its records in `v2.1-*` (CP102) and no phase updates the brief; an agent following the brief literally reads the wrong plan section and writes to the wrong log.
- **Fix**: Add a step to Ph11 (or a coordinator pre-step): update `phase-brief.md` to the 2.1 paths, or have §0.1 state "where the brief says v2-X read v2.1-X; commit trailers follow the current session attribution".

### PS11 — Ph17 (and Ph11) are too large for one agent session; split before starting
- **Section**: §3 Ph17 (~1 600 lines stated), Ph11 (~1 500).
- **Problem**: Ph17 bundles TextureView layout + rotation transform + zoom/pan for three screens + `PdfRenderer` viewer + text viewer + `TvMenuOverlay`/`ZoomMode` + no-PC home + slideshow options + fixtures + 6 JVM and 7 new instrumented classes + 4 adapted ones. The real work is a multiple of the stated lines; earlier phases were interrupted by usage limits (phase-brief "Records"). Ph11 adds `EventLog`, shipper, PC endpoint/store/migration, ~80 existing clickable sites for tap ids (I counted 76 `onClick`/`clickable` hits under `ui/`), catalogue, version bump and CI path changes.
- **Fix**: Split Ph17 into 17a (TextureView/portrait/zoom/menu, PlayerRules) and 17b (documents, no-PC home, slideshow options, fixtures); optionally split Ph11 into 11a (catalogue, `EventLog`, PC endpoint, version) and 11b (tap ids, shipper, `WrongDialog`, Settings). Each ends green on its own; ordering in §3 stays valid (Ph18 needs both 17s).

## Low

### PS12 — `pc.yml` change as written would run from the wrong directory; two pytest roots without `__init__.py` can collide
- **Section**: §4.2, CP124.
- **Problem**: `pc.yml` sets `defaults.run.working-directory: pc`, and the collect-logs step uses `../`. The plan's step `python -m pytest -q -ra pc/tests tools/tests` would not find `pc/tests` from `pc/`. `pc/tests` and the planned `tools/tests` have no `__init__.py`; in one invocation duplicate basenames (`test_package.py`, `test_readme.py` appear in Ph19's list, but exist in `pc/tests`) or a second `helpers.py` give "import file mismatch".
- **Fix**: Add a second step `python -m pytest -q -ra tools/tests` with `working-directory: .`; keep `test_package.py`/`test_readme.py` in `pc/tests`; use unique names under `tools/tests`. Same for `package`'s Linux step.

### PS13 — Two more existing PC tests assert `2.0.0`
- **Section**: CP104, §1.1 `pc/tests/`.
- **Problem**: `pc/tests/test_http.py:22` (`version == "2.0.0"`) and `test_platform.py:205` ("Ferry 2.0.0 started") fail once `VERSION = "2.1.0"` (Ph11); only `test_request_log.py` is listed. The Ph11 agent would fix them on first red CI, but "never weaken a test" makes the intent worth stating.
- **Fix**: List `test_http.py` and `test_platform.py` as adapted-for-version in Ph11.

### PS14 — `check_manifest.py` needs no change and fixture regeneration is unnecessary
- **Section**: §1.6, §4.6, CP106.
- **Problem**: The script checks "required present / forbidden absent"; it does not reject extra components, permissions or providers (only `uses-library` and `WRITE_EXTERNAL_STORAGE`). WorkManager's merged `SystemJobService`, receivers, `InitializationProvider` and `RECEIVE_BOOT_COMPLETED` already pass. The `manifest-xmltree.txt` fixture is regenerated from a release APK that the agent cannot download (only from the job-log dump).
- **Fix**: Drop the change; the Ph15 agent just confirms `check_manifest: OK` in the CI log. Keep the fixture as is.

### PS15 — `UploadItemFactory.fromShared()` does not exist
- **Section**: §1.4 `media/UploadItemFactory.kt`, M4.
- **Problem**: The real methods are `fromPick`, `fromUri`, `fromMedia`, and `mapToMedia` (documents URI → `getMediaUri`, else `_data` lookup in `MediaStore.Files`). Step 3's name+size+date lookup is new, but steps 1–2 largely exist.
- **Fix**: Say "split `fromUri`/`mapToMedia` into `ShareResolver` + `MediaStoreLookup`", and keep the 2.0 `_data` path as a step in the decision table so `ShareToFerryTest` and `GpsOriginalTest` stay unchanged.

### PS16 — `KeyInjectionTest` reference "recorded by a host step `input_keys`" is not possible
- **Section**: Ph16 tests.
- **Problem**: Host steps run before/after a class (the activity is not running before it; the next class starts with `am force-stop`). A host-recorded reference cannot be compared inside the test.
- **Fix**: Compare in-test: `UiDevice.pressDPad*` (what `TvHelpers.press` already uses) versus `MainActivity.injectKey`, each from a freshly shown Home, and assert the same focused card. Drop `input_keys`.

### PS17 — Removing `Remote` is a larger test change than "adapted for the TV button"
- **Section**: §0.1 regression rule, Ph18 ("adapted `CastLoopbackTest` + `PhoneScreenshotTour`").
- **Problem**: `CastLoopbackTest` waits for `screen(sc) == Screen.Remote` three times, taps Remote's Pause/+10 s/Play, and the notification tap "opens the Remote"; `PhoneScreenshotTour` shoots the Remote states; `MainActivity.OPEN_REMOTE`, the Home "cast running" card and `CastService` content intent point at `Screen.Remote`. All of this changes with the controller (M21), not just a button.
- **Fix**: In Ph18 list `OPEN_REMOTE` (keep the extra as an alias opening the Controller), the Home cast card, and say `CastLoopbackTest`'s Remote assertions are rewritten against the Controller with the same TV-side checks.

### PS18 — Guide build: artifact download can fail the `package` job; artifact layout is not stated
- **Section**: §4.8, CP123.
- **Problem**: `actions/download-artifact@v4` errors when the artifact does not exist (an emulator job failed before any screenshot; `if-no-files-found: ignore`). The plan says "(if present)" with no mechanism. The upload path `ci-out/*/screenshots/` keeps a `phone-try1/screenshots/…` prefix when both attempts produced files; `build_guide.py --shots <dirs>` must accept that and decide between attempts.
- **Fix**: `continue-on-error: true` on the two download steps; `build_guide.py` searches recursively by file name and prefers the later attempt dir. Estimate: pixel_6 PNGs (1080×2400) at 30 shots plus TV 1080p shots will likely exceed the 10 MB target before base64 (+33 %); decide the JPEG fallback in Ph19's first run, not after.

### PS19 — "checks about every 15 minutes" is probably untrue on the real phone
- **Section**: M5 text, `ResumeScheduler` (§1.4), V3 (honest messages).
- **Problem**: WorkManager periodic work is deferred by Doze and App Standby buckets (a rarely used app can be limited to hours, "restricted" to about a day); aggressive OEM management on vivo adds more. CI cannot show this (the test forces the job), so the notification text will be wrong in exactly the overnight case the feature is for.
- **Fix**: Word it "checks every so often" (or "checks regularly, at least when the phone wakes"), keep the 3-day rule, and add the real-device timing to `docs/v2.1-handoff.md` (item the user verifies once).

### PS20 — Harness details the Ph15 agent will trip on
- **Section**: §4.4, §1.6.
- **Problem**: (a) `PIDS` is an unnamed array, so `stop_pc NAME` has no name→pid map. (b) `start_pc` does `cp -r "$ROOT/pc" "$d/pc"` into an existing `$d/pc` (a nested `pc/pc`) and truncates `console-$name.txt`; a separate `start_pc_again` is needed. (c) A failed PartA leaves PC-A down for later classes; `after` runs unconditionally, but the restart must be in a step that always runs. (d) Suite lines split on `|`, so `before`/`after` strings cannot contain a pipe (`grep a|b` in steps). (e) `pidof app.ferry` assertion after `am kill` is moot (see PS1).
- **Fix**: Add an associative array `PC_PID[NAME]=$!` in `start_pc`; write `start_pc_again` to skip the copy and reuse folders; put `start_pc_again A` in the `after` of every class that calls `stop_pc`.

### PS21 — `CastSkewTest` against a hand-written "2.0 TV" stub tests the author's memory of 2.0
- **Section**: CP128, §4.5.
- **Problem**: The stub encodes what the plan believes 2.0 does (400 for unknown actions, ignore unknown keys). That is true today (`ControlRequest.ACTIONS` check in the 2.0 `CastReceiverServer`), but Ph16 edits that file, so the stub is the only record.
- **Fix**: Before Ph16 changes it, copy the current `CastReceiverServer` validation into `core/src/test/.../LegacyCastReceiver.kt` and run the skew test against it (a real frozen 2.0 behaviour, 40 lines).

## Phase order and interfaces (summary of checks)
- Ph11 → Ph19 ordering holds: catalogue and `EventLog` before any logging use; `ZoomState` (Ph14) before Ph17; `CapsCheck` (Ph16) before Ph17/Ph18; `ControlBus`/state (Ph16) before the controller (Ph18); WorkManager first used in Ph15 only.
- Each phase can compile on its own provided PS3 (ringLog accessor) is handled in Ph11 and `CastSink.onControl`'s changed return type is changed together with `CastSinkImpl` and `:core` test fakes in Ph16 (the plan does this in one phase).
- Ph12's host check `readable-line --expect "GPS yes"` works without phone headers (PC derives it from the EXIF bytes), so Ph12 does not depend on Ph14.
- Emulator traffic reaches the PC as loopback (QEMU NAT), so `first_phone_seen` (non-loopback rule, M9/C6) is never set during emulator suites; the QR-once behaviour is covered by pytest only. Acceptable; note it in the Ph12 build log so nobody expects an emulator proof.
