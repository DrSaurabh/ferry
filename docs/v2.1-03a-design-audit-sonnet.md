# Ferry 2.1 design audit 03a (reviewer 1: platform, data safety, PC, testability)

Artifact: `docs/v2.1-02-design.md` (rev 0). Reviewer: Sonnet. Focus: Android/Fire OS feasibility, data safety (V1), PC correctness, CI testability.
Verified = checked in the repo or by a Python run. "uncertain" = from platform knowledge, not checked on a device.

---

## S1 — High — §5.4 pending copies — V1, V4
Design copies shared `uri:` items into `files/pending/` only after the 10-minute foreground wait. H53 and requirement P13 say copy "while waiting" because a share grant expires when the share ends.
The grant is forwarded to the service via the start-intent ClipData (`SendCoordinator.start`, verified), so it lives only as long as that service instance and process. If vivo kills the process in minutes 0–10, or the service dies for any reason, the grant is gone and the queue holds URIs that can no longer be read. The shared photo is never sent, and the user was told "waiting".
The original stays in the gallery, so nothing is destroyed, but the queue silently loses user intent.
Fix: copy at the moment the engine enters WaitingForPc, or at share time when no PC is reachable, not at minute 10. Keep the free-space check, with "Share again when the PC is on" as the fallback. Delete a copy only after the PC answers saved/skipped, and on Cancel.
Also: when a queued item cannot be opened later (grant lost, media row deleted), the row must say so in plain words instead of failing as a generic error. The queue also needs a schema version and an atomic write (tmp + rename).

## S2 — High (uncertain) — §3 H67 TextureView fixes B3 — B3
The F17 symptom is a tall box with a sideways picture, i.e. the decoder ignores `rotation-degrees` while Media3 already sized the box with the rotated size.
On API 21+ Media3 normally reports `unappliedRotationDegrees = 0` because it assumes the codec rotates, and `PlayerView` rotates a TextureView only when that value is non-zero. A TextureView therefore probably does not rotate on a decoder that ignores the tag. The decoder output reaches a SurfaceTexture with no rotation either way. The design states "Media3 applies the rotation tag itself" as fact. The field-test doc only said "to verify".
The emulator decoder honours the rotation (the field-test doc itself warns of this), so `PortraitVideoTest` would pass on the emulator whether or not the fix works on the stick (see S15).
Fix, smallest:
- Keep TextureView, because zoom needs it anyway.
- Log `Format.rotationDegrees`, `VideoSize.unappliedRotationDegrees`, view size and first-frame time (already in L1).
- Name a fallback now: either `ExoPlayer.setVideoEffects` with a rotate effect (needs media3-effect, AndroidX, GL cost on the weak stick), or transform the TextureView manually from `videoFormat.rotationDegrees`.
- State plainly in the decision log that B3 is judged from the first real-stick log, not from CI.
Without this the design may ship a "fix" that changes nothing.

## S3 — Medium — §4 PdfRenderer page bitmap — V8, V1 (stability)
"Render at 2× screen width, one page + neighbours": an A4 page at 3840 px wide is about 3840×5430×4 B ≈ 83 MB per bitmap.
- Three of them cannot fit in the Fire stick's app heap (256 MB class; uncertain).
- A bitmap taller than the GPU texture limit (usually 4096 or 8192) makes the hardware canvas refuse to draw it ("trying to draw too large bitmap").
- `PdfRenderer` allows only one open `Page` at a time, so "neighbours" must be rendered sequentially and cached.
Fix: `Page.render(bitmap, clip, matrix, RENDER_MODE_FOR_DISPLAY)` supports rendering only the visible viewport with a zoom matrix. Use one viewport-sized bitmap (≤ 1920×1080), re-render on zoom or pan (scale 1–4×), and fill it white first because the render leaves transparent areas. This makes ZoomState for PDFs a render matrix, not a graphicsLayer scale. Cache at most the current page. Close the renderer and page in `onDispose`. SecurityException (password-protected PDF) is already covered by "can't be shown".

## S4 — Medium — §5.2 step 2 name+size match, and the risk line in §12 — V1, V5
The F11 failure is a share where the gallery hands over something Ferry cannot open as an original. If the shared URI is a gallery-made copy (re-encoded, or GPS stripped), its size will not equal the MediaStore original, so the "exactly one DISPLAY_NAME + SIZE row" match fails in exactly the case being fixed. If it is a FileProvider URI onto the real file, it works. Which one vivo does is unknown (uncertain). The design needs the diagnostic either way.
Conversely, §12 accepts "same name and size ⇒ same bytes" for exact duplicates only. A match is sent *instead of* what was shared, so a different photo with the same name and size would be sent silently. That is unlikely for camera names but possible for WhatsApp/downloaded names.
Fix:
- Log first, which is the stated purpose of H70, and make the log a "first-class output of 2.1": scheme, authority, path shape, which step resolved it, whether sizes matched, exceptions.
- Step 2 should also compare `DATE_TAKEN` or EXIF `DateTimeOriginal` when sizes differ, and refuse with "sent as shared" if there is not exactly one candidate.
- Step 1 must pick the Images or Video collection from the row's MEDIA_TYPE (query the Files table by id), not by guess.
- The row text must differ for "original used (matched)" and "sent as shared" so L6 can see which path ran.

## S5 — Medium — §5.4 WorkManager details — V4, V5, V8
1. A unique work name cannot hold both a periodic and a one-time request. Use two names, or have one self-rescheduling one-time worker.
2. "On network change" is not a WorkManager trigger. A one-time request with `NetworkType.CONNECTED` runs immediately when the phone is already on Wi-Fi, and only once. The PC returning does not change the phone's network. Real behaviour is therefore "within ~15 min, later in Doze" (battery exemption helps; vivo may still defer).
   - The notification text "will send when Ferry is running there" should say "checks every ~15 minutes".
   - The worker should re-enqueue a delayed one-time request when it finds nothing, or the design should simply say periodic only.
   - Requirements P14 also says "on network change"; the requirement and the design disagree with the platform here.
3. The engine gives up after 30 min (B20, `UploadEngine` header, verified) and its state is in-process. §5.4 must say how the engine hands "still waiting" to `SendQueueStore` without a Finished or failed state, and how the Home banner and Cancel read the queue.
4. A user force-stop (vivo "clean up", Settings > Force stop) cancels all jobs until the next launch. "Resumes after the app was closed" is true for swipe-away and reboot, not force-stop. Fine for a home tool, but the Waiting notification must not promise more (V5).
5. A Worker on cold start needs `AppGraph` initialised (done in `FerryApp`, so probably fine) and multicast lock + network binding for the one 2.6 s discovery. Screen-off Wi-Fi power-save can drop broadcasts, so try the remembered address first (the design does). Uncertain.
6. `android/ci/check_manifest.py` asserts the merged release manifest; WorkManager merges `RECEIVE_BOOT_COMPLETED`, its `InitializationProvider`, receivers and `SystemJobService`. The script allows extras for permissions, but check the service/provider asserts. Add `ResumeSendWorker` to the CI manifest checks.
7. The Android 12+ background-FGS rule: a user-granted battery-optimisation exemption is on the exemption list (I believe, uncertain on exact wording). The design's fallback "tap to send" notification is right. The `PendingIntent` for the tap is fine because notification-tap starts are exempt.

## S6 — Medium — §1.4 key injection — V7
Main-thread `activity.dispatchKeyEvent` is correct (the design says main thread; the server thread must post to it). Details that bite:
- Build events with the full constructor and `SystemClock.uptimeMillis()` (downTime/eventTime), not `KeyEvent(action, code)`, so Compose and `TvKeys` timing/repeat logic behave.
- KEYCODE_BACK via `dispatchKeyEvent`: on API 33+ with the back-invoked callback (targetSdk 35) the real Back is routed through the window's `OnBackInvokedDispatcher`, not `onKeyUp`. An injected event at Activity level may not reach `BackHandler` (uncertain). The Fire stick is API 28 where it works, but the CI TV emulator (API 30) and the phone suite differ from the real device.
- Fix: for `back`, call `onBackPressedDispatcher.onBackPressed()` directly (the same call the phone uses, H69). Inject only D-pad/OK/Menu.
- `home` is "Ferry home screen" so it is not a key at all. Say so in the table.
- `Menu` and Rewind/FF keys: after injection they must reach the same handler as the real remote (TvKeys). `KeyInjectionTest` should assert that injected and real `adb shell input keyevent` produce the same screen, and run on API 30 TV.

## S7 — Medium — §1.4 TvCaps — U7, V5
- On API 28 (Fire OS 7) `isHardwareAccelerated`/`isSoftwareOnly` do not exist (API 29). `MediaCodecList(REGULAR_CODECS)` also lists software decoders (`OMX.google.*`, `c2.android.*`) which claim large sizes (e.g. HEVC up to 4096×2304 in software), so caps would say "4K fine" and the stick would stutter or fail. Filter software decoders by name prefix (`OMX.google.`, `c2.android.`, `c2.goldfish.` for emulators) and report the best of the remaining hardware decoders.
- `isSizeSupported(w,h)` is orientation-sensitive in some implementations. Compare using (max side, min side) and also `areSizeAndRateSupported(w,h,30)`, so portrait 2160×3840 is not rejected against a 3840×2160 limit.
- The phone's `MediaMetadataRetriever` width/height are the stored (unrotated) values; the design lists `ROTATION` (good), so state explicitly that dims are swapped for 90/270.
- Make the verdict "too large" only a warning with "Play anyway" (the design already does).

## S8 — Medium — §7.2 LogShipper — V11, V8
1. Offsets and rotation: the device log rotates at 2.5 MB ×2. A persisted byte offset into `ferry-app-log.txt` is wrong after rotation (the file it pointed to is now `.1`). Persist `(session id, last shipped seq)` and ship from whichever file holds it, or make `seq` monotonic across restarts. Say what is shipped when the cursor's data was rotated away (ship what exists, log a gap marker).
2. Lost-ack duplicates: if the PC stored the chunk but the response was lost, a retry duplicates lines. Send the offset or seq range in a header (`X-Ferry-Log-From`) and let the PC drop already-stored ranges (it can keep last-seen per device in a tiny file or the file size).
3. Chunking: a 512 KB chunk must end on a newline.
4. A 2.0 PC answers 404 to `/api/v1/logs`. Treat 404 as "PC too old; stop trying for this session" and do not retry every 10 min. Add this to the compat tests.
5. "Ship at app background" is best-effort: the process can be frozen within seconds. Do it in a short coroutine with a 5 s timeout; the "after a send finishes" trigger (in the service) is the reliable one.
6. Volume: Detailed-by-default logs polls and `ctl.tx` at 1 Hz. At about 100 B/line a controller session is ~360 KB/h, so 5 MB of device log holds only about 14 h and the PC 20 MB per device fills fast. Exclude state polls even in Detailed (log only changes of the polled state), otherwise L6's rules (e.g. "same button ≥3× in 5 s") drown in noise and rotation eats the interesting part.

## S9 — Medium — §8 QR "until the first phone connected" — U6, V4
`State.first_phone_seen` hooked to `TransferTracker.seen_client` (verified: it fires for any request, including a browser, the phone's browser fetching `/`, or the TV's Downloader fetching the APK). The QR would disappear before the phone ever has the app, and before the TV install finishes.
Fix: set the flag only on a request that carries `X-Ferry-Device` (the Ferry app itself), from a non-loopback address. Persist it in `ferry-state.json` (already `State`).

## S10 — Low/Medium — §7.3 batch summary — L5
The summary line counts "3 already on PC", but duplicates found by `check-batch` never reach `/api/v1/upload` (the engine marks them AlreadyOnPc beforehand, verified in the engine header). The summary built from upload requests alone will always show 0 already-on-PC. Also:
- Two upload workers run in parallel, so "i == n" is not "last to finish"; count completed items against n.
- A cancelled or failed batch never reaches n; the 60 s idle flush is therefore the normal path and needs a timer thread, not just a check on request arrival.
Fix: send `X-Ferry-Batch` on `check-batch` as well (or carry the duplicate count in it), count completions, flush on n or 60 s idle.

## S11 — Low — §8 /tv and /app redirects — B4
- `/` is the install page and `/app` already streams the APK (`ROUTES_EXACT`, verified). "`/app` with a Fire TV UA → 302 `/app/Ferry.apk`; browsers keep the page" does not describe the current routes: the page is at `/`, and `/app` has no page. The redirect for a TV UA on `/` (page) or `/app` (to the `.apk` URL, which only changes the URL Downloader sees) is what matters, since Downloader decides by URL/extension. Correct §8 and the test list.
- UA match `"AFT" in ua` is a substring (also used by `device_type`, so it already exists); `\bAFT[A-Z0-9]+\b` is tighter. Downloader's own UA is the WebView/device UA (uncertain whether it contains `AFT…` on Fire OS 7). So also keep the plain `/tv` alias as the primary documented URL.
- Send a relative `Location: /app/Ferry.apk` (no host reconstruction; avoids `Host` header problems) with `Content-Length: 0`. HEAD must also redirect. Both follow the existing `send_response` wrapper, so the request log still records it.
- Add `/tv` to `ROUTES_EXACT`; `test_removed_routes.py` may assert the route set, so update it.

## S12 — Low — §7.3 PC logs folder, keys — L3, L7
- Device folder names: verified with Python that the existing `sanitize_name(raw, dest_dir, is_win=True)` makes `..`/`.` → `file`, `CON`/`AUX`/`nul.txt`/`com1` → `_CON` etc., strips RTL/control chars, takes the last path component of `a/b\c`, and trims trailing dots/spaces. Reuse it (with `dest_dir=logs` for the path-length cap); the design only says "safe device name". A request without `X-Ferry-Device` should land in `unknown`, not the UA label.
- Collisions and renames: two phones of the same model give the same default name ("vivo V2413"), and the optional rename (H76) splits one phone's history across two folders. Add a short per-install id to the folder (`vivo V2413 (a3f9)`), sent as `X-Ferry-Device-Id`. This also helps friends (V13).
- The 200 MB cap "oldest removed" must exclude the `ferry-logs-*.zip` files and must not delete the file currently being written; the zip must exclude `*.zip` (otherwise each zip contains the previous ones). Use a collision-proof name (`-HHMMSS` or suffix) so Z twice in one minute does not replace a zip (V1 spirit).
- Zipping while logs are appended is fine (verified: a file that grows during `zipfile` writing yields a valid archive with all bytes read). Run Z on a worker thread; do not block the key reader or the console.
- `msvcrt` keys: read only when `sys.stdin.isatty()` (a redirected or `pythonw` start has no console; `kbhit` misbehaves). Use `msvcrt.kbhit()` polling every ~100 ms in a daemon thread. This coexists with the existing `input("Press Enter to close...")` only on exit paths. Ignore keys while a prompt is up. Keys must go through `Console` (the sole stdout writer, verified).
- Migration of `ferry-log.txt` and `ferry-log.1.txt` into `logs\`: do `os.replace` at start before `RequestLog` opens it; when the move fails (OneDrive lock) keep writing the old place and note once. A read-only Ferry folder is already handled by `_note_once`.
- EXIF: the existing `exif_gps_status` reads the GPS IFD only; the new DateTimeOriginal needs the 0x8769 Exif sub-IFD, then tag 0x9003 (ASCII `YYYY:MM:DD HH:MM:SS`). Read from the saved temp file's first 128 KB (an APP1 segment is ≤ 64 KB, so 128 KB is enough unless a large APP segment precedes it), and bounds-check every offset (the existing code relies on `except Exception → "unknown"`, which is acceptable). Keep the "unknown/none/zeroed" distinction in the log line, not just yes/no. Fixtures: with GPS, without GPS, zeroed GPS, big-endian (`MM`), truncated.

## S13 — Low/Medium — §1.1 volume — R5, V7
`AudioManager.adjustStreamVolume(STREAM_MUSIC, …, 0)` on a Fire stick may do nothing: a stick on HDMI/CEC often has fixed volume where the TV handles loudness (uncertain; the requirement already says the TV may not follow). Use `isVolumeFixed()` (API 21) and `getStreamMaxVolume`; if fixed, report `volume: null` in state and hide the volume row in the controller (V7: nothing shown that cannot work). Keep the mute action to `ADJUST_MUTE`/`ADJUST_UNMUTE` (API 23+; fine for minSdk 25), not toggle.

## S14 — Low — §5.4 / Android 15+ dataSync limit — V8
targetSdk is 35 (build.gradle, verified). On Android 15+ a `dataSync` foreground service has a ~6 h cumulative limit per 24 h and the system calls `Service.onTimeout(int,int)`; if the service doesn't stop in a few seconds it fails with a `RemoteServiceException`. A normal send is minutes, so risk is small, but a very large batch over slow Wi-Fi, or the 10-min wait repeated, can in principle hit it. Implement `onTimeout` (API 35) to save the queue, stop the service and hand over to the Worker. One line in the design and a unit test of the hand-over function are enough. API 36 adds no new rule I know of for this case (uncertain).

## S15 — Medium — §11 testability in GitHub Actions
Existing CI: phone emulator API 34 google_apis, TV emulator API 30 android-tv, API 25 emulator; several emulator-runner invocations per job with the PC on the host (`android.yml`, verified). The Fire stick is API 28 and not available.
| Test | Verdict |
|---|---|
| WaitForPcTest with process kill | Not as one JUnit test: the instrumentation shares the app's process, so killing it kills the test. Feasible as a staged job: (1) instrumented part A starts a send with no PC and asserts the queue file and Waiting state; (2) host script `adb shell am force-stop app.ferry` (or `am kill`); (3) start `pc/ferry.py` on the host; (4) trigger the job with `adb shell cmd jobscheduler run -f app.ferry <id>` (WorkManager `TestDriver` works only in-process, so it cannot cover the kill); (5) `verify_inbox.py`-style check on the host. Discovery by UDP broadcast does not work through the emulator NAT; use the remembered/explicit address `10.0.2.2:8765`. Also test "with exemption" (`adb shell dumpsys deviceidle whitelist +app.ferry`) and "without" (default) separately, which covers both branches of S5 item 7 on the API 34 emulator, which enforces the background-FGS rule. |
| PortraitVideoTest | Feasible (`TextureView.getBitmap()` is easier than SurfaceView's PixelCopy), but vacuous for the real bug: emulator decoders honour the rotation (S2). Add a JVM test of the rotation-to-transform helper if S2's manual fallback is adopted; otherwise label the test "does not prove B3 on the stick". |
| KeyInjectionTest | Feasible on the TV emulator; compare with real `adb shell input keyevent` (S6). |
| ZoomPanTest (photo/video/PDF) | Feasible: assert the transform state plus sampled pixels (video via `TextureView.getBitmap`). Needs a fixture PDF; `make_fixtures.py` can write a minimal one in plain Python (hand-assembled PDF, no library needed). |
| PdfViewerTest | Feasible; PdfRenderer is on the API 25 emulator too. |
| ShareOriginalTest | Feasible with a test FileProvider (in `androidTest`) giving a GPS JPEG; it proves the resolver logic only, not vivo's actual URI form (S4). Keep the log of the real form as the proof. |
| ControllerTest with a loopback TV | Feasible, same process, no kill. |
| BackEverywhereTest | Feasible; keep it separate per phone/TV, since the phone's Back and the TV key path differ. |
| Lock-screen/notification actions (R9) | Only the notification actions can be asserted (UiAutomator on the shade); not a real lock screen. |
| Version skew (2.0 phone ↔ 2.1 TV/PC and the reverse) | Missing from §11. Add pytest and JVM cases: a 2.1 phone against a TV answering without `api`, 400 for `open`, and a 404 from `/api/v1/logs`. |

## S16 — Low — compatibility, small points
- Version name: `app/build.gradle.kts` builds `2.0.$run` (verified); the requirement says 2.1.0 and A2 prints "Ferry 2.1.0". Update the rule and `VersionRuleTest` together.
- 2.0 TV ↔ 2.1 phone: `ignoreUnknownKeys` makes new fields safe, and an old TV answering 400 to unknown actions is handled by the `api < 2` rule. A missing `api` field must be read as 1 (state it).
- §3 applies `graphicsLayer` to the `AndroidView`. Compose draws the host view into its own layer, which works for TextureView on hardware canvases, but I can't confirm it with PlayerView's overlay controller (uncertain). Cheaper and more predictable: scale/translate the TextureView or PlayerView directly in the `AndroidView` `update` block (`scaleX`, `translationX`) and clip the parent.
- Lock-screen controls (R9): on Android 13+ the media-style lock-screen UI is driven by a `MediaSession`. Plain notification actions show in the shade and on the lock screen as an ordinary notification (visibility public needed), not as a media player (uncertain). Acceptable, but the design should say which one it means.
- `Settings.Global.DEVICE_NAME` is public from API 25, so it is fine for minSdk 25. `Settings.Secure "bluetooth_name"` is not readable on Android 12+, so it just falls through to "Maker Model" (harmless).
- `ACTION_MANAGE_UNKNOWN_APP_SOURCES` needs the `package:` URI data to open Ferry's own row.
- §5.5 asks for location "in one system dialog sequence". On Android 13+ ACCESS_MEDIA_LOCATION is requested together with the media permissions; on API 29–32 it is a separate prompt. `PermissionPlanner` already encodes this; keep it as the single source (uncertain on exact grouping on API 36).
