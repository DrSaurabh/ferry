# Ferry 2.1 (Stage A) — Design audit, reviewer 2 (Opus)

_Reviews `docs/v2.1-02-design.md` (rev 0) against `VISION.md` (V1–V13), `v2.1-01-requirements.md` (rev 1) and the user's own findings `v2-field-test-feedback.md` (F1–F36). Focus: vision alignment, simplicity/UX for a non-developer, scope, battery, logging usefulness. Finding IDs O1…; severity High/Medium/Low. "uncertain" = not verified._

## Findings

### O1 — High — §2 / §5 (P14) — V8: the phone's own cast session never ends and holds locks while paused
**Problem.** P14 (the user's own battery concern, F24 "idea 5") requires: a Play-on-TV/controller session ends after **10 min with nothing playing**, and wake/Wi-Fi locks only "while serving a playing video". The design states the 10-min rule only for the new PC-sourced "follow-only" mode [H66]. For the ordinary phone cast it is silent, and today's code (`service/CastService.kt`, `start()` → `locks.acquire()` for the whole session; `follow()` polls the TV every 3 s while hidden, forever, until the TV goes idle) keeps a partial wake lock (4 h timeout) + Wi-Fi lock and a 3-s poll loop for a paused cast left on the TV overnight. That is exactly the "TV session left running, phone serving the video" case F24(d) names.
**Fix.** State in §2: `CastService` (both modes) ends the session after 10 min of `playing=false`/idle (log `svc.stop reason=idle`); locks are held only while `playing=true` for a video cast (release on pause, re-acquire on play; a photo slideshow needs the file server but not a wake lock beyond the request handling); background poll slows to e.g. 10 s when no Ferry screen is visible. Add a unit test on the idle rule.

### O2 — High — §7.1 / §7.4 (L1, L6) — V11: logs cannot reliably pair intent with outcome, so "normal use + log review" (F30) can't judge real use
The whole 2.1 acceptance (§9 of the requirements) rests on the review script. As designed it will produce mostly guesses:
1. **No intent→outcome catalogue.** L6's first and most important signal, "action started with no result", is left as "rules exactly as L6 lists". Which events are intents and which events count as their outcome (and within what time) is never defined. Without it the script either flags everything or nothing. Needed: a small table in `docs/v2.1-log-events.md`, e.g. `tap send_photos → screen picker (2 s)`, `tap send (picker) → send.start (5 s)`, `send.start → send.done | send.wait | send.cancel`, `ctl.tx action=X → ctl.ack id (3 s) and, for key/seek/zoom, a TV state change seen by the next poll`, `tap cast → play first_frame | err.shown (15 s)`, `perm ask → perm result`, `wrong` marker, etc. The script then implements the table; tests use it.
2. **No correlation ids across devices.** `ctl.tx/ctl.rx/ctl.ack (action, ms)` have no request id, and phone and TV clocks are not synchronised (seconds of skew are normal on a Fire TV stick). Merging by time (§7.4) will misorder phone→TV pairs. Fix: phone puts `id` (seq) into every control request; TV logs `ctl.rx id=… result=applied|ignored:<why>`; and on each log upload the PC returns its time so each device logs `clock pc_offset_ms=…` (the script shifts lines). Same `batch` id already designed for sends — extend the idea.
3. **"TV didn't react" ≠ HTTP 200.** F30 asks for "controller command sent but TV didn't react". A 200 only says the request arrived. The TV's `ctl.rx result=` (e.g. `ignored: no zoomable screen`) gives the real answer.
4. **Remote vs phone keys are indistinguishable.** Injected keys go through the same `dispatchKeyEvent` path (H62), so TV `key` lines can't tell whether the user used the remote or the phone controller — the single most useful fact for judging whether the controller "earns its place" (V12). Log `key … src=remote|phone`.
**Severity reasoning:** this is the mechanism that replaces manual testing; without 1–3 the user will be asked "how did it go?" again, which F12/F30 explicitly rule out.

### O3 — Medium — §7.1 (L1) — V11: events missing that the review needs; one noisy event
Missing from the fixed event list:
- `dialog` (name, choice): needed for L6 "same dialog twice in a row" (the F11 loop was a *dialog*, not an error) and "Discard N picks?" outcomes. `err.shown` only covers errors.
- `notif` (posted / tapped / action): "Saurabhs-PC is back — tap to send", lock-screen controls, "vivo stopped the send" — otherwise their effect can't be judged.
- `work.run` (ResumeSendWorker: started, PC found y/n, ms) and `poll.start/stop` (controller/cast polling, discovery retry loop): needed to verify P14 from logs as F24 promises ("idle time with something running shows up in the review").
- **Last exit reason** at `app.start`: `ActivityManager.getHistoricalProcessExitReasons` (API 30+, no permission) tells whether the previous process was killed by the system, crashed, ANR'd or was swiped away. This is the cheapest reliable source for L6 "app killed mid-task" and for U9 ("only if Ferry detected that the system stopped a send"), and settles F1's open question (is the vivo Recents lock needed?) from normal use.
- `play` stop **reason** (user stop / back / error / ended / phone left): L6 "video stopped < 10 s after start" is meaningless without it.
Noise: in Detailed mode `ctl.tx` for every 1-s state poll ≈ 3 600 lines/hour of controller use, burying real events and eating the 5 MB cap during a film. Log poll *changes* (state transitions, failures) only, even in Detailed.

### O4 — Medium — §2 / §5 (P14) — V8: discovery retry back-off not designed
P14 requires "discovery retries run only while a Ferry screen is visible and **back off after 1 min**". The design never mentions it. Today `MainActivity` runs `retryIfNotFound()` every `AUTO_RETRY_MS` (10 s) for as long as the activity is STARTED, with no back-off (verified in `MainActivity.kt` l.57–64). On the TV that is harmless (mains power), on the phone it is the F24(c) cost. Also TV home "Silent retry every 10 s continues (H45)" (§6) is fine on TV but the rule must be per-device.
**Fix.** One line in §5.4/§2: phone retries every 10 s for the first minute after a screen becomes visible, then every 60 s; reset on user action/`ON_RESUME`/network change; log `disc` with `retry=n`. Unit-test the schedule.

### O5 — Medium — §2 (R9) [H66] — V8/V12: "follow-only" foreground service is heavier than needed
For PC-outbox items opened from the controller, the design starts `CastService` as a foreground service on the **phone** that serves nothing, only to show lock-screen controls, and stops "at idle/home or after 10 min with nothing playing". For a 2-hour film from the PC this is a 2-hour foreground service with a polling loop (interval in background unspecified) on the phone, for something the phone isn't doing. R9 says lock-screen controls "while something is playing on the TV **from this phone's session**"; a PC-sourced item is explicitly not the phone's session (H63: "the phone leaving does not stop it"). It also duplicates polling: `ControllerViewModel` polls every 1 s while visible and `CastService` follows too (today it switches 1 s/3 s via `remoteVisible`), so two pollers exist for one TV.
**Fix (smallest).** Drop follow-only mode: lock-screen controls only for phone casts (where a service already runs). The controller screen covers PC-sourced playback. If kept, specify a slow background poll (≥10 s) and make `CastService` the single poller that the controller reads from.

### O6 — Medium — §2 Layout (R2, R8) — V3/V7: explicit arrow/OK buttons missing; one-finger pan missing; screen likely overcrowded
- R2 asks for the touch pad **plus explicit ↑↓←→ and OK buttons** (the touch pad alone is not discoverable for a non-developer and fails "usable without looking" for precise single steps in menus). The layout lists only "Back / Home / Menu row".
- R8 says "drag pans when zoomed". The design uses **two-finger** drag for pan, one-finger swipe stays an arrow key — which on a zoomed photo means "next photo" (and the zoom resets, §3). A non-developer will drag with one finger to look around and lose the photo. Use the TV state: when `zoom.level > 1`, one-finger drag = pan, tap = OK; the explicit arrow buttons remain for keys.
- Height budget on a ~900 dp phone: status (~100 dp) + pad 45 % (~400) + Back row (56) + video card (slider + 5 buttons + Stop ≈ 160) + zoom row (48) + volume (56) + Browse (56) ≈ 880 dp before adding R2's arrow buttons → scrolling, which a remote must not need. The user said video playback is what matters most (F35 answers). Suggest: arrow buttons as tappable edge arrows *on* the pad (no extra height) with OK in its centre; when a video/slideshow is playing, the context card sits directly under the status line and the pad shrinks (≈ 30 %); volume as a compact row in the card's header.
_Height numbers are estimates — uncertain until the screenshot tour shows it; add the controller with a video playing to the tour and check nothing scrolls._

### O7 — Medium — §2 Entry / §5 Home — V12: two TV entries on Home (Play on TV + TV remote) where one would do
Home will have Send photos & videos, Send files, From PC, **Play on TV**, and a new **TV remote** button; the controller's Browse sheet then offers "From this phone" (= Play on TV) and "PC outbox" (overlapping From PC's list). R1 asks for "a **TV** entry"; R11 "one controller UI". Two buttons with overlapping meaning is the kind of choice V12 calls a defect, and a non-developer will not know which to press to "watch something on the TV".
**Fix.** Replace "Play on TV" with one **TV** button that opens the controller; when nothing is playing the controller opens the Browse sheet first (tabs "From this phone" / "From PC"). Keeps the picker flow, removes a Home button. If the design keeps both, at least say why in the decisions log.

### O8 — Medium — §3 (T7, L4, A2) — V7/V11: Menu overlay content and reach
- The Menu overlay lists Zoom / Slideshow speed / Shuffle / Date / Something's wrong / About on viewer, player **and** doc. Speed/Shuffle/Date mean nothing on a video or PDF → V7 "anything that can't be used is not shown". Make items per screen: video = Zoom, Something's wrong, About; slideshow = Zoom, Speed, Shuffle, Date, …; doc = Zoom, …
- The overlay exists only on viewer/player/doc, but §9 says "TV Menu > About" and A2 requires "home menu > About", and L4's TV "Something's wrong" must be reachable on **every** TV screen (home, cast screens, PC-not-found, errors — the moments most likely to be wrong). Define Menu on TV home (About, Something's wrong) and on cast screens.
- L4 also requires "Something's wrong" in the phone **notification while sending/playing**; §5.3/§2 notification actions omit it.
- Zoom is the most-used item: put it first and focused, so zoom is Menu → OK (two presses), close to T7's one-press intent. While zoomed but not in zoom mode, keep a small "Zoom 2× · ☰ to change" badge so a cropped picture never looks like a fault (V5).

### O9 — Medium — §10 (U5) [H76] — V3/V13: the device-name chain is what 2.0 already does, and it produced "V2413"
2.0 already sends `Settings.Global.DEVICE_NAME`, falling back to `Build.MODEL` (`AppGraph.deviceName`, l.92–96, sent as `X-Ferry-Device`, used by `pc/ferry.py` l.260). The field test still showed **"V2413"** (F6), so on the user's vivo `DEVICE_NAME` came back empty. The design's chain adds `Settings.Secure "bluetooth_name"` (likely not readable by a normal app on Android 12+ — **uncertain**) and a "Maker Model" fallback that gives "vivo V2413" — the design's own examples (§7.3 "from vivo V2413", §10) show the F6 complaint unfixed. The optional rename field in Settings is the only part that will help, and nobody will find it.
**Fix.** Keep the chain, but when it ends on the model fallback, show the name once where the user already is — e.g. on the setup's last step: "This phone will appear on your PC as **vivo V2413** · Change" (typing once per device is allowed by V2; skipping keeps the default). Log which source the name came from (`device_name src=global|bt|model|user`). TV: same once on first start (or settable from the controller's text field, R6).

### O10 — Medium — §5.2 (B2) [H70] — V5: "the sharing app removed it" can be untrue
Step 4 shows "Sent without location — the sharing app removed it" when the shared stream has no GPS "but the item is a camera photo". (a) "Camera photo" is not defined; (b) when the original couldn't be resolved, Ferry cannot know whether the original *had* a location — photos taken with camera location off, screenshots, WhatsApp images all lack GPS, so the note blames the gallery falsely (V5: messages must name the **real** cause). 
**Fix.** Show the note only when evidence exists: the shared stream has EXIF `Make/Model` (a camera photo) and no GPS **and** resolution failed; word it "Sent as the sharing app gave it — its location may have been removed. To keep locations, send from Ferry's own picker." Log `share.resolve step=… gps_in_stream=…` so the review can see how often it happens (if never, drop the note).

### O11 — Medium — U7 TV side / U8 — V5/V7: two requirement items not designed
- **U7 second half**: if a too-big video still fails on the TV, the TV must say "This video is 4K/8K — too large for this TV stick" instead of the 2.0 "can't play this video format (HEVC)" — the exact wrong-cause message the user hit (F16). §2 covers only the phone's pre-check; §1.4 computes `TvCaps` but no TV error mapping uses them. Fix: `PlayerRules` maps a decoder error + (video size from the format > caps) → the size message; otherwise the existing format message. Test with a fake format/caps pair (JVM).
- **U8 gear removal**: not mentioned. 2.0's `TvPlayerScreen` hides next/prev/subtitle but not the settings button (F19). Since §3 re-inflates `PlayerView` from XML anyway, state there how the settings button is removed (e.g. a `controller_layout_id` without `exo_settings`, or hide that view by id) and add an assertion to the TV screenshot/MenuOverlay test that no settings view is visible.

### O12 — Medium — §5.4 (P13) [H53] — V4 (overlaps data-safety reviewer): shared items copied only after 10 min
Shared items are copied into `files/pending/` only when the 10-min foreground wait ends. The URI grant from the share intent is tied to the receiving component/process; if vivo kills Ferry during those 10 min (F1 shows it does), the grant is gone and the item can only become "Share again" — the user's F20 ask ("keep its work") fails silently for exactly the items the requirement singles out. Fix: copy shared items as soon as the send enters `WaitingForPc` (not after 10 min), with the same free-space rule. Cheap; removes a race. _Grant-lifetime detail uncertain on vivo; the change is safe either way._

### O13 — Low — §2 / §5.1 (U1) — V6: two different "Back"s and "Home"s on the controller screen
The controller has the phone's top-bar Back (leaves the controller) and a **Back** button in the "Back / Home / Menu" row (TV Back), plus a **Home** (Ferry home on the TV) next to the phone's own Home. A non-developer will press the wrong one. Label the TV row clearly ("TV Back", "Ferry home on TV", "TV Menu", with a small TV icon), and say in §5.1 that phone system Back on the controller leaves the controller **without** stopping what plays (V6) — and is never sent to the TV.

### O14 — Low — §5.5 (U2, U9) — V3/V5/V13: setup wording and maker-specific card
- Step 4 ("Allow Ferry to install its updates") lands on a system page with a switch and no way forward but Back; tell the user what to do there: "Turn on **Allow from this source**, then press Back." Same for step 3 if vivo shows its own battery page instead of the standard dialog (uncertain).
- The kill card is titled "vivo stopped the send" and its steps are vivo's; the design says `StopDecision` detects this, but `StopDecision` only arbitrates `stopSelfResult` ids — the detection is `Prefs.interruptedCount` (TransferService l.130/143) — fix the reference so the builder doesn't look in the wrong place. For V13 (friends' Samsung/Pixel), show "Your phone stopped the send" with the vivo steps only when `Build.MANUFACTURER` is vivo, generic battery steps otherwise. Use O3's exit reason to show the card only when the system really killed Ferry.

### O15 — Low — §5.4 (P14) — V8: background check has no end
`ferry-resume-send` runs every 15 min (plus on connectivity) until the PC appears — weeks if the user forgot the send. Use `NetworkType.UNMETERED` (the PC is only on Wi-Fi; avoids runs on mobile data) and after e.g. 3 days post one notification "1 send still waiting for Saurabhs-PC — Keep waiting / Cancel" and drop the periodic part if not answered (the queue itself stays — V6). Requirement-conformant and lighter.

### O16 — Low — §5.6, §1.1 — V5: jargon and dead-end messages
- Preview top line "3840×2160 · 0:42 · **HEVC**": the codec name is jargon and is the very word the user learned to distrust (F16). Show "4K · 0:42" (and the warning); keep codec in the log.
- "Update Ferry on the TV" (old TV, api < 2) names no next step: "Ferry on the TV is older than on this phone. On the TV, open Ferry and choose **Install update**." (if the 2.0 TV offers that; else point to the guide's TV update steps).

### O17 — Low — §7 (L2) — requirement gap: PC detail level
L2 asks for the Normal/Detailed setting on the PC too; §7.3 has none. Simplest consistent answer: the PC always logs at "Detailed" during the trial (no setting, V12) — say so explicitly, or add one console key. Not worth a GUI.

## Checked, no finding (brief)
- Key injection into Ferry's own window (H62) is the simplest way to make the controller equal the remote everywhere; fits V7/V12 and Level 1 only.
- TextureView for both B3 and video zoom (H67) is one change for two requirements — good economy; the dropped-frames log covers the 1st-gen-stick risk.
- 4-step setup with "Skip" and later one-line "Fix" banners matches F4/U2 and V4; the existing "choose Allow all" rationale (`media_rationale`) should simply be kept in step 1.
- Transfer screen Back = go Home, send continues; "Discard N picks?" — consistent with V6.
- TV home without PC ("Ready for your phone") — matches F28(a)/T9.
- PC: QR only until first phone + "press A", tip only after a failure, `/tv` alias, Z = zip logs — all minimal and match F13/F14/F15/F30.
- No new third-party libraries; WorkManager is the AndroidX-only addition P13 needs.
- Scope: apart from O5 (follow-only service) and O7 (duplicate Home entry), nothing is heavier than the requirements; no non-goals pushed.
- Nit: the review script's rules are named "R-1…R-11", colliding with the controller requirements R1–R11 — call them S1…S11.
