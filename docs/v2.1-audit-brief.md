# Ferry 2.1 (Stage A): audit brief (give this to every reviewer)

**Read first:** `docs/handoff/VISION.md` — the approved vision and rules V1–V13. Work that conflicts with it is a defect. Name the rule (V1…V13) each finding relates to.

**What Ferry is.** A personal home tool for ONE user (Saurabh Sawhney, a non-developer) and later a few friends, to move and enjoy photos/videos/files over home Wi-Fi between an Android phone (vivo X200 Pro, Android 16 / API 36), a Fire TV Stick HD 1st gen (Fire OS 7, Android 9, 1080p, weak GPU) and a Windows 10/11 PC. 2.0 is built and field-tested: one APK with phone + TV layouts (Kotlin, Compose, Media3), and a Python stdlib program on the PC. 2.1 fixes field-test bugs and adds: phone-as-TV-controller, zoom/pan on TV, PDF/txt on TV, sends that wait for the PC, setup with all permissions, thorough usage logging shipped to the PC, and a log-review script (testing = normal use + log review instead of manual checklists).

**Where things are.** Repo `/home/claude/ferry`: `pc/ferry.py` (PC program), `android/app/src/main/java/app/ferry/…` (app; `ui/tv/` TV screens, `cast/` TV control server/client, `upload/` send engine), `android/ci/` (CI helpers), `docs/`. Inputs: `docs/v2.1-01-requirements.md` (rev 1), `docs/handoff/v2-field-test-feedback.md` (F1–F36, the user's findings), `docs/v2.1-00-research.md`, `docs/v2-decisions-log.md` (H51–H76 are 2.1 decisions). The 2.0 design is `docs/v2-02-design.md` (unchanged parts stay).

**Priorities (in order, from VISION).** 1 data safety → 2 works first time / simplicity → 3 honest messages and consistency → 4 battery/lightness → 5 speed → 6 maintainability → 7 new features.

**Explicit non-goals (do NOT recommend).** Auth, pairing, encryption, TLS (pairing is Stage B, not 2.1). Cloud/internet. Multi-user. Play Store. iOS, Linux/Mac. Controlling the Fire TV outside Ferry or its power. Editing files; Office documents. Background PC program, GUI, self-update, destination folders (all Stage B). Enterprise hardening, telemetry leaving the home. Features beyond the requirements.

**Constraints.** Builds and tests run only in GitHub Actions (no local Android SDK; emulators: phone API 36 and a TV image). PC: Python stdlib only. Android: only AndroidX/Media3/Coil/OkHttp/Compose. Claude maintains everything; the user never reads code.

**How to review.**
- Review `docs/v2.1-02-design.md` against the requirements and VISION. Read existing code where a design claim depends on it (e.g. what `CastReceiverServer`, `UploadEngine`, `TvPlayerScreen` really do today).
- Report concrete problems: wrong, missing for a requirement, contradictory, risky on the real devices, over-complicated, or untestable in CI. For each: ID (prefix given to you), severity High/Medium/Low, design section, VISION rule, problem, suggested fix (smallest that works).
- Verify by cheap experiment where possible (run Python, grep the code, check API facts you are sure of). Mark anything not verified **"uncertain"**.
- Don't rewrite the design or edit any file except your report. Write the report incrementally to the path you are given.
- Keep it proportionate: a home tool. Prefer fewer, important findings over many trivial ones.
